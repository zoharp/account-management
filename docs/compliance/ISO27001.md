# account-management — ISO/IEC 27001:2022

What this app does for ISO 27001, in two senses that are easy to confuse:

1. **The app as a system in scope.** The control plane administers every tenant on the platform,
   so it is itself an Annex A asset. §2–§4 map its controls to Annex A with the evidence for each.
2. **The app as the ISMS console.** The **ISO 27001 audit** screen (`/iso27001`) is where the
   results of the `compliance-audit` Claude skill are browsed and closed out, for *any* internal
   system. §5–§7 are how that screen works.

## 5. The ISO 27001 audit screen

### 5.1 What it is for

The `compliance-audit` skill scans a repo, its Supabase, Fly and Vercel config, asks the operator
about what cannot be scanned, and writes `compliance/ledger.json` in **that system's repo**. A file
on one machine cannot be browsed, assigned or closed out. `iso27001_controls` is the durable,
multi-system home for those results; the screen is how a person reads them and records an answer
the scan cannot give — *is it documented? is the DPA signed?*

### 5.2 Two statuses, never merged

| Column | Set by | Meaning |
|---|---|---|
| `status` | the skill (seed / import) | The automated verdict from the last run. **This app never writes it.** |
| `resolved_status` | an operator, via *Resolve* | What the operator asserts after answering. |

They are kept apart on purpose: a later import cannot wipe a human answer, and a human answer
cannot quietly overwrite a scan result. An auditor sees both side by side. The headline *% compliant*
is computed from `status` only — resolving a control does **not** raise the score. Re-running the
skill is what does.

### 5.3 Data model

`iso27001_controls` (sql/005) is the **current** view: one row per `(system_name, control_id)`.
`system_name` is an internal product key (`orcanos-qms`, `traceability-matrix`), **not** a customer
account. History is sql/006: `iso27001_audit_runs` + `iso27001_run_controls` (each imported run and
its immutable snapshot) and `iso27001_control_notes` (every save, append-only). Columns in
[SCHEMA.md §8–§9](../../SCHEMA.md#8-iso27001_controls).

### 5.4 API

| Route | Does | Guard | Audited |
|---|---|---|---|
| `GET /api/iso27001?system=<key>` | All controls for one system, sorted numerically (`A.5.2` before `A.5.10` — PostgREST sorts lexically) | `requirePlatformStaff()` | No — reads are not recorded (SECURITY.md §8.3) |
| `PATCH /api/iso27001/:id` | Save an answer: `resolution_answer` (required), `resolution_evidence_link` (http/https only), `resolved_status`, `resolved` (`false` = comment, control stays open). Appends a note **first**, then updates the row | `requirePlatformStaff()` | `iso27001_control_resolved`, with `control_id`, `system_name`, `resolved` — group *Compliance* |
| `GET /api/iso27001/:id/notes` | That control's full answer history, newest first | `requirePlatformStaff()` | No |
| `GET /api/iso27001/runs?system=<key>` | Saved runs, newest first | `requirePlatformStaff()` | No |
| `GET /api/iso27001/runs/:id` | One run and its control snapshot | `requirePlatformStaff()` | No |
| `POST /api/iso27001/runs` | Import `{system_name, ledger}`: validate all-or-nothing, write run + snapshot, upsert automated columns of the current view (never a resolution column) | `requirePlatformStaff()` | `iso27001_run_imported` |

`resolved_by` stores the master `users.id` and `resolved_at` the server time; neither is taken from
the request.

### 5.5 Using it

1. **ISO 27001 audit** in the sidebar. Header line: *% compliant · open gaps · resolved of total*.
2. Filter by theme (Organizational / People / Physical / Technological), status, and open/resolved.
3. Click a control's title → the resolve dialog shows the automated evidence and which skill checks
   produced it.
4. Answer in plain words, paste an evidence link (policy page, signed DPA, drill record), pick the
   status the answer implies, save.

**Evidence links should point at something durable** — a Drive document, a GitHub file at a commit,
a ticket. A link to a local path or a chat message is worthless to an auditor six months later.

### 5.6 Limitations to know

- **Runs are imported, not triggered.** The skill runs in Claude Code on someone's machine and
  writes `compliance/systems/<key>/ledger.json`; the screen's *Import run* loads it. Running a scan
  from the web (e.g. a GitHub Actions job the screen dispatches) is not built.
- **Import is not transactional.** Run → snapshot → current-view upsert over PostgREST. A failed
  snapshot deletes its run; a failed upsert answers 502 with the run kept and the current view stale
  (re-import to fix).
- **A past run shows today's answers**, not the answers as they stood then — reconstruct those from
  note timestamps in the control's history.
- **The % compliant score uses the automated `status` only**, as before.

## 7. Adding a system (including this one)

1. Add `{ key, label }` to `ISO27001_SYSTEMS` in `src/lib/iso27001-systems.ts`. An import for any
   other key is refused.
2. Create `compliance/systems/<key>/scope.yaml` **in this repo** (see
   `.claude/skills/compliance-audit/SKILL.md`), with `repo_path` pointing at the system's checkout.
3. Run `/compliance-audit` for that system. It writes `compliance/systems/<key>/ledger.json`.
4. On the screen: pick the system → *Import run* → that file.
5. Bump the version and add a release note if code changed.

Recommended next runs: **Traceability** (scope already in place) and **account-management itself**,
to replace §3 with a real ledger.
