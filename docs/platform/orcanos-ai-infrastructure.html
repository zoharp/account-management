Operational reality

Five differences that have actually cost us time.

⚠ VercelAn environment variable change does nothing until you redeploy. Vercel snapshots variables into each deployment. Change the value, reload the site, and you still see the old one — then an unrelated code push picks it up and it looks like the code fixed it. Order is always: change the variable, then redeploy. Cost on 2026-08-30: two deploys to change one string.
⚠ Cloud RunSecrets must be in cloudbuild.yaml, not just on the running service. gcloud run services update works immediately — and is erased by the next build.
⚠ Supabase + VercelVercel cannot open a direct Postgres connection. db.<ref>.supabase.co publishes only an AAAA record; Vercel functions are IPv4. The error is getaddrinfo ENOTFOUND, which reads like a typo in the hostname. The fix is the pooler: aws-0-<region>.pooler.supabase.com:5432, user postgres.<ref>.

Fly restarts on fly secrets set

Which invalidates every issued admin token. Usually fine — know it before doing it mid-day.

Some settings fail loudly, some silently

JWT_SECRET missing = the container will not boot, obvious. ASK_PAUL_SSO_SECRET missing = the app runs perfectly and one button fails. That one went unnoticed for weeks.

How a request is routed

Every call carries X-Account. Middleware looks the account up in master case-insensitively, and returns 403 if unknown or inactive — it never falls back silently. It then decrypts that account's vector-DB key and LLM key into ContextVars, so everything downstream automatically hits the right customer.

Users are global

users lives only in master, keyed by email. Per-tenant tables store the user id as a plain bigint with no foreign key — there is deliberately no users table in a tenant database.

What this buys

Documents and embeddings are physically separated. Strong isolation, easy deletion, easy to explain to an auditor.

What it costs

Every new customer is a real, billable Supabase project that must be provisioned — and deleting the account does not remove it.

Tenancy · Traceability

One database for everyone.

How it works

One SQLite file serves every account. Rows carry an account_id; the tenant name is the Orcanos Virtual_dir. The id is computed locally: sha256("<url>|<virtual_dir>")[:32].

Writers are the scarce resource

SQLite has one writer. WAL mode is mandatory, not an optimisation — a matrix_cache blob can exceed 1.4 MB, and a session refresh writes on every authenticated request.

Cache is budgeted per account

DB_CACHE_BUDGET_MB evicts an account's oldest pages, so one busy tenant cannot fill the disk. Eviction only costs speed — the page rebuilds.

What this buys

Cheap and fast. It started as an on-premises IIS app, where per-customer databases made no sense.

⚠ Two silent failuresIsolation is enforced by code, not by the database — every query must be account-scoped, and a missed scope is a data leak. And an empty allowlist table means the access gate is OFF, not that nobody is allowed in.

Data residency.
EU and US.

Added 2026‑09‑10 — the largest change to the platform since this deck was written. One deployment per region, a signpost that grants nothing, an automatic hand‑off before the password, and a migration that counts rows before it deletes anything.

The reason

We hold our own copies of their personal data.

Orcanos holds the requirements. But our databases hold copies — and that is what a residency guarantee is about. We are the processor; the tenant is the controller.

WhereWhat personal data is in it
matrix_cache · source_cache · funnel_cacheTrainee names, emails, roles, completion dates — training snapshots
quiz_attempts · quiz_answersSomebody's exam record — the one thing Orcanos cannot rebuild
sessions.auth_headerThe user's real Orcanos credential, encrypted
Ask Paul's per-customer SupabaseThe customer's document text and its embeddings
One value decides it all. accounts.region — 'us' or 'eu' — lives once on the master database and is read by all three apps. A customer has one region, not three settings that can drift apart. It is chosen at creation and cannot be changed by editing the field: rewriting it moves no data, it only records the customer as living somewhere they do not.

⚠ Why not one app, two machinesA Fly volume is pinned to one region and is never shared between machines. fly scale count 2 does not give you a region — it gives you two divergent databases with nothing reporting the split. Nothing replicates between the two apps. That is the feature, not an omission.
⚠ Half-shipped releasesdeploy.bat deploys the US app only. A release is not shipped until both commands have run — and because both regions serve real customers off the same build, a version drift produces no error anywhere. Only a customer in one region seeing something the other cannot.
SELF_REGION is the whole of an instance's identity. Two apps sharing one value is a deployment mistake nothing else would catch, so GET /api/admin/regions returns self_region and the console checks it.
Standing up a region

Two steps that silently void residency.

⚠ The bucketTigris distributes objects globally by default. An EU database's write-ahead log lands on US edges while every other part of the deployment looks correct. Restrict the bucket to EU regions, or point LITESTREAM_BUCKET at an EU-only S3/R2 bucket. Nothing in the app can detect this, and it is still unverified from the CLI today.
⚠ The open doorA fresh region is open to everyone until its allowlist has one row. An empty account_access fails open by design — right for a first install on a laptop, exactly wrong for a new public Fly app. traceability-matrix-eu answered allowed to every tenant for the minutes between its first deploy and its first row. The fix: write the denied sentinel row zz-gate-closed (allow_access: 0) before announcing the URL. It makes the count non-zero, so the gate turns on without granting anything.
Both belong in a region-standup checklist, not in someone's memory. They are ranked R1 and R2 in the handbook's residency next-steps list.
Getting the customer to the right place

One address for everyone. The region is our problem.

Each instance holds only its own region's tenants, so an EU tenant has no account_access row in the US database at all — and the old code told them “Access is not allowed. Please contact us to open an account.” False, and a dead end.

The directory

account_region

Two columns — tenant → region — held identically in every instance. A name and a region string. No personal data, so copying it across the border transfers nothing.

Load-bearing

It grants nothing

account_access is still the only permission gate. region_check() treats a missing entry as “no idea”, never as “here”. That is what makes the console's cross-region write safe to do best-effort. Never consult it in a gate.

⚠ Before the passwordCredentials POSTed to the wrong region are themselves a cross-border transfer of personal data — even though that instance refuses them and stores nothing. So the check hangs off POST /api/auth/check-account, which already fired on URL blur, and /login answers 409 with the correct URL, not 403: nothing is wrong with the account, the request arrived at the wrong deployment.
⚠ rr=1 is not theoreticalThe two instances hold separate copies of the directory. If they ever disagree — a half-finished move, a directory write that failed on one side — an automatic redirect bounces the browser between two servers forever, each certain the customer belongs to the other. The loop guard means “you have been sent once already”: fall back to a panel with a link and let a person decide.
Migration

“Move to the EU” is a physical migration, not a flag.

freeze → export → import → COMPARE ROW COUNTS → restore access → update master + directory → purge

Order is the safety. The purge is last, so a short import stops the move with the source fully intact. The import is one transaction — a half-landed import is the state that would make “may I delete the source?” unanswerable.

DecisionWhy
The table list is discovered from the schemaIt grows every few releases. A hand-maintained list is correct the day it is written and silently short after — and short here means a customer's quiz attempts stay on the wrong continent while the move reports success

Authentication

Google sign-in, and the gate behind it.

The flow, in four steps

1 — The app calls GET /api/auth/config (public) to learn which methods this account has enabled, from the auth_methods table.
2 — It generates a random state, stores it, and redirects to Google.
3 — Google returns to our redirect URI with a code.
4 — The server exchanges the code, checks state matches, and issues our own JWT.

⚠ Two things to knowThe redirect URI must be registered on the OAuth client of the account named by PLATFORM_ACCOUNT — for Account Management, https://accounts.orcanos.ai/auth/callback. And the state check is a hard failure here: Ask Paul used to skip it for a legacy path, but skipping it in a new app only buys a CSRF hole.

The staff gate

user.role === 'admin'
  && user.email.endsWith('@orcanos.com')

Three properties never to weaken

1. API routes answer 404, not 403. A non-staff caller must not learn the routes exist.
2. role and email are re-read from the database on every request, never trusted from the JWT — so revoking an admin takes effect immediately, not in 24 hours.
3. The page-level check is not the boundary. Pages redirect for UX; the route handlers protect the data.

Diagnosing sign-in

The login error message is deliberately useless.

What the user sees

Invalid credentials

Every failure path returns exactly this: missing user, no orcanos_user_name, wrong password, wrong tenant, not an Orcanos admin, identity already linked.

Why

So the route cannot be used to enumerate users. This is deliberate and should stay.

⚠ How to actually diagnose itRead the security_audit_log table. The distinguishing reason goes there and only there. The screen cannot tell you anything — ever.
A worked example. Orcanos sign-in to the control plane had never worked. Both causes returned the same message: the users row carried someone else's orcanos_user_name (test data), so every password was being checked as another person's; and the tenant was pinned to the wrong one. Only the audit log said so. It was fixed on 2026-08-30 — the successful event is timestamped 01:43:32Z.

Caching

Five rules, and what to ask when "the data is wrong".

Smart refresh escalates by itself

Inside the same job, and it says why: no stored rows, no Updated/Created date column in the filter, a source that errored or truncated, or a merged count that no longer matches Total_records — which is the only signal a deletion produces.

An export renders the snapshot

It never re-reads Orcanos and never builds. An export is exactly as fresh as the last refresh, no more.

Quiz results are overlaid at read time

A newly passed quiz shows without a rebuild, while the cached JSON stays pure Orcanos.

A background job outlives its page

Closing the tab kills the polling, not the job. GET /api/matrix/{id}/active-job is how a returning page re-attaches. One job per user; exports have their own slot so a download cannot block a rebuild.

matrix_cache, funnel_cache, export_jobs, ai_jobs, pending_traces can all be deleted — they rebuild. Which is exactly why they are also the tables we would not migrate to Postgres.

How /security-scan works — verification-first

1. A grep hit is a lead, not a finding. Read the sink and trace the source.
2. Separate CONFIRMED (unsanitised sink + reachable untrusted source, both seen) from PLAUSIBLE (depends on something unread).

4. Re-run the scan on the diff.

Security · v3.44.0, 2026-09-10

A password with a default is a password everybody has.

/admin is a FastAPI route on the same public host as the app, registered before the SPA catch-all. Everything below follows from that one fact: the admin console is on the open internet, and one shared password stands in front of it.

⚠ What we foundADMIN_PASSWORD used to fall back to a literal written in the source. Every deployment that had not set the secret was fully administrable by anyone who had read the repository — and a working login looked identical whether the password was configured or guessed. It now answers 503 when unset, on login and every authenticated route. Set it on both regions before deploying, or /admin 503s the moment it ships.

A staged per-IP throttle

10 failures → 5 minutes · 15 more → an hour · 25 more → permanent block. Checked before the password is compared, so a correct password during a pause is still refused — which also stops the lockout being a timing oracle for "this guess was right".

The temporary stages are process memory; the permanent block is a database row, because a permanent block a restart clears is not permanent.

The escape hatch matters

A permanent block can lock out the only admin, and the Release button lives inside the console they can no longer reach. Starting the process once with ADMIN_UNBLOCK_ALL=1 clears the table and logs loudly that it did.

Reading the blocked list fails open: a database hiccup must not be what locks an admin out.

⚠ The read-only table browserOff unless ADMIN_DB_BROWSER=1 — its blast radius is every row in production. Injection is prevented by membership, not escaping: no WHERE, no ORDER BY, no query box, and the table name is checked against what sqlite_master actually returns before it is interpolated. The connection runs PRAGMA query_only = ON. sessions.session_id is the bearer cookie, so it and auth_header, csrf_token and ai_config.api_key are redacted by name — plus any column whose name looks like a secret. A missed entry is not a visible bug; it is a silent disclosure on a page reachable from the internet. Add the column to the redaction list in the same commit that adds the table — and never add a filter box.

User manual · Account Management

Signing in, the list, creating and editing.

Signing in

To get in at all you need both: role = 'admin' on your master users row, and an @orcanos.com email. Everyone else gets a 404 on every route, by design.

For Orcanos email sign-in you also need orcanos_user_name set on your row — set by an admin, directly in the database; there is no self-service screen yet. The first field accepts that username or your email, and QW_Login is always called with the stored username, never with what you typed.

The accounts list

Every tenant, one row: name, status, database, data region, module licences, spend. Module columns come live from the Traceability instance — a dash means "no answer from that source", which is not the same as "off".

The region column is read from the instance that actually holds the data, not from what was recorded. When the two disagree the row is flagged as a conflict — one of them is wrong and nothing here can tell which. Since 0.6.0 the account name opens one window with six tabs: Overview, Orcanos, Traceability, Ask Paul, LLM, Spend.

Creating an account

The Orcanos tenant is parsed out of the API URL, and the form shows you which one it decided on. With no URL there is no tenant, and the licence pills stay disabled.

Since 0.3.3 every creation writes the Traceability account_access row, even with nothing ticked — without that row the tenant cannot sign in to Traceability at all. A database is optional since 0.3.0, and an account created without one is created inactive.

The Data Region is required and has no pre-selected value, and it cannot be changed afterwards. Creating an EU account is refused while no EU Traceability instance is configured. The new account is then signposted in every region, best-effort.

Moving an account to another region

Behind a button, because it happens once in an account's life if ever. The seven steps appear as soon as the tenant name is typed — so the plan is readable before the move is authorised — and each is ticked off with the row counts actually moved.

Tell the customer three things first: everyone signed in gets signed out; their Ask Paul vector database does not move; and the source copy is deleted only after both sides' row counts match. Afterwards, check that region's secrets before believing a bug report.

⚠ Four editing rulesA blank password field means "keep the stored secret" — an empty string would wipe a working credential. A new vector key cannot be saved until it tests green, and editing any vector field clears the previous result. {success: null} is a third state — "nothing configured to test", not a failure. The Status switch writes is_active and is therefore an Ask Paul control despite its label.
